# Version 2 contracts

## Current contracts: method 3.0 in the existing pipeline

`extraction.records[].kind` is the single nine-option statement type. `labels.risk_functions` replaces `drr_phases` and `resilience_functions`; `assertion_kind` and `documentation_status` are rejected in new outputs. Label arrays require unique selections. The schema title records the vocabulary version. Existing directory names identify the pipeline, not a frozen vocabulary version.

Archived validation uses each saved schema and retains legacy semantic checks. New field gaps cannot replace populated values, source conflicts or processing coverage. Examples are synthetic; `legacy-profile.json` is a frozen older-method compatibility fixture. The live local worker preserves source records and proposes relationships; canonical identities and the reference SQL remain deferred blueprints, not current runtime behavior.

Sixteen schemas generated by `scripts/build_v2_contracts.py`. The generator reads the authoritative `config/v2/taxonomy.json` and `vocabulary.json`; it never writes them. It also generates the topic catalogue. Edit JSON for categories and Markdown for prompts, then run `python scripts/method_pack.py build`. Edit the generator only when changing output structures; do not hand-edit generated schemas. See [the customization guide](../../docs/CUSTOMIZATION.md).

Model output schemas: triage, translation, extraction, labels, reconciliation, quality, report, comparison, workplan and chat. Twelve prompt routes share these ten contracts. Application-owned schemas: document-version, source-segment, canonical-commitment, run-request, release and dashboard.

All object keys are required, nullable unknowns are explicit and extra keys are rejected. These are portable local JSON Schemas; provider adapters must verify their actual strict-output subset and do a real canary. Schema syntax checks do not establish provider compatibility or factual correctness.

Every model task emits proposals. The application resolves original quotes and locations, normalizes scoped local IDs, verifies field evidence/links, preserves source records and proposed links and wraps results with real source/run provenance. The model cannot create a trusted validation receipt. `release` separates automatic eligibility from optional human audit. `dashboard` restricts performance to not_assessed for this NDC/NAP product.

The v2 offline validator checks a subset of rules: shapes, allowed labels, quote resolution, numeric normalization, basic field references/detail links, owned-segment accounting, required report sections and citations. Semantic support, translation fidelity and extraction recall require source-oriented assessment. Current source authorization, saved-bundle and pin behavior are documented in the architecture guide.

Report citation membership is checked **only when** the caller supplies `known_evidence_ids`, `known_record_ids` and `known_commitment_ids` from the frozen bundle. Without them, report checks establish citation presence, not resolution. `check_v2_pack.py` supplies these sets for the synthetic fixture. None of these checks certifies that a quotation supports a finding.

The prepared release contract now requires each stage's origin run, source versions, validation receipt reference, archived method components and prepared request reference/hash. A reused stage retains its original metadata. These fields include blueprint capabilities; the local worker and archive behavior are described in the architecture guide.

Run `scripts/check_v2_pack.py` and `python -m unittest discover -s tests -p '*v2.py' -v` with the project dependencies available. The fixtures in `examples/v2/` are synthetic, never actual country results. The v1 registry, schema generator and inventory still exist for historical/reference work; they are not silently migrated by generating v2 contracts.
